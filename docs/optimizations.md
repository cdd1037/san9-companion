### 商业、开垦与巡察目标

#### 商业目标

商业工作检查原本比较当前商业值与城市上限。注入改为提供一个动态目标上限；没有在这里直接修改城市商业、最大商业或实际收入。

1. 季节索引为1时直接返回0，即4—6月通常不会通过商业未满的工作条件。
2. 其他季节，先取军团资金减去下一季前所需俸禄。正余额按`min(所属城市数, 20) × 1500`分档。
3. 正常数值范围内，令档位`q = floor(正余额 / 分档金额)`。`q > 0`时返回`原上限 × (9 - min(q, 8)) / 8`；否则保留原上限。代码还有`军团+0x24 == 1`时绕过财政缩放的分支，已确认为内政导向方针；它仅绕过资金缩放，不绕过季节门。见[商业、开垦与巡察目标](optimizations.md#companion-audit-26)。

例如所属10城，扣俸后余额60000，档位为4，原上限1000会变成AI目标625。当前商业700的城市即使没有达到真实上限，也可能不再安排商业。这与“增加电脑金钱”或经济分隔点是不同机制。

**证据：**[商业载荷](../recovery/evidence/payload_disassembly/00421680_000A2700_6A.asm)，路径`0x004B3456 → 0x000A2700`；[安装入口](../src/runtime/RuntimeInjection2026.cpp:582)。[旬前载荷](../recovery/evidence/payload_disassembly/00421230_000A1000_2D4.asm)调用`0x46AA50`保存季节索引；[日期解码研究](../../remake/research/findings/RE-SAN9PK-0041.md)确认索引含义。

#### 开垦准入

同样修改AI工作检查的上限返回值，而非直接修改收获公式。

- 季节索引为2时返回0，即7—9月通常不安排开垦。
- 计算`到下一次七月的天数 + 510`所对应的军粮消耗，再减去当前粮食。若为正缺口，并且军团360日收获预测仍小于该缺口，返回真实开垦上限，使未满的城市保持候选资格。
- 未进入上述粮食紧缺分支时，计算`T = 100 - floor(当前开垦 × 100 / 开垦上限) + floor(兵役人口 / 1024)`。随机余数`rand % 100 < T`才返回真实上限，否则返回0。

例如开发程度80%、兵役人口10240时，阈值为30，对应随机准入约30%；阈值达到100后，此随机门不再淘汰候选。通过本门不代表一定执行，还受后续人员和工作条件限制。

**证据：**[开垦载荷](../recovery/evidence/payload_disassembly/00421C84_000A3900_85.asm)，路径`0x004AB6E6 → 0x000A3900`；[安装入口](../src/runtime/RuntimeInjection2026.cpp:583)。城市字段含义见[都市结构研究](../../remake/research/findings/RE-SAN9PK-0008.md)。消耗与收获调用分别为`0x43EDE0`、`0x43DA80`。

#### 方针与巡察

军团`+0x24 == 1`明确为内政导向模式，见原版策略更新器及[原版AI研究](../../remake/research/ai.md)。商业载荷在该模式下绕过资金充足导致的目标缩小，仍保留4—6月的季节门；因此不能称为完全绕过商业限制。

民心方面已定位到`0x4AAE0F → 0xA1FD0`：AI巡察的“是否已满”检查读取城市配置的民心上限，替代固定1000；同一助手也用于界面及命令资格。当前证据支持上限联动，不能再凭旧帮助扩写一套尚未找到的“商业、开垦、巡察统一收益评分”。

证据：[民心比较载荷](../recovery/evidence/payload_disassembly/00425944_000A1FD0_27.asm)、`codeMaxPeopleHeartCmp`的上传与相关挂接、原版巡察目标选择`0x4AAE30`。恢复名不等于独立AI策略。

### 电脑探索的目标内容与发现后登用

#### 探索范围

电脑根势力的探索计划临时换用新的辖区谓词。候选地点有归属时比较其根军团与执行方根军团；地点无归属时，进一步检查所属都市的归属。由此可跨同势力副军团辖区安排探索。

执行方根势力带玩家标记时，跳过该谓词替换，继续原路径。因此不能写成“所有玩家委任军团都自动获得同样的全势力探索范围”。也不是全地图无条件探索，不能据此推导隐藏人物、事件、宝物全开放。

**证据：**[探索范围载荷](../recovery/evidence/payload_disassembly/004223E0_000A1F00_78.asm)，路径`0x004B6BE1 → 0x000A1F00`；内部谓词入口`0x000A1F32`；[安装入口](../src/runtime/RuntimeInjection2026.cpp:646)。内容过滤已确认读取隐藏人物计数，并以未发现宝物数量作后备；电脑探索即时登用失败还保留判定前增加的忠诚，见[电脑探索的目标内容与发现后登用](optimizations.md#companion-audit-30)。不等于开放全部历史事件。

#### 目标内容与即时登用

探索范围与目标过滤分别处理。对非玩家根势力，先读取建筑`+0x148`，它是隐藏人物表的计数；非零就保留候选。为零时再枚举地点的未发现宝物，宝物数量非零也可保留。玩家根势力回到原版谓词，原版检查人物集合及其人物条件。此目标内容门与是否允许电脑实际取得宝物仍是不同层次。

字段链为`建筑+0x58`内嵌单位、单位`+0xE4`隐藏人物表、表头`+0x0C`计数，合为`+0x148`。原版`0x435BC0 → 0x460FD0`与探索结果门`0x494B50`共同确认该含义；宝物路径为`0x452F50 → 0x46FE80 → 0x46FDE0`。

探索人物的即时登用另在`0x4946E6`接入`0xA1FA0`。电脑掷骰失败时，它把“接受登用交互”的局部标志置0，使后续失败路径不再把目标对探索势力的忠诚强制写为49；判定前已经增加的忠诚保留。玩家路径及电脑成功路径不做此改写，发现后的身份/位置转换也未被取消。这不是直接提高登用成功率，也不是24号普通行程登用命令。

证据：[内容过滤](../recovery/evidence/payload_disassembly/00422480_000A1D70_51.asm)、[即时登用改写](../recovery/evidence/payload_disassembly/004224F8_000A1FA0_29.asm)、[原版登用研究](../../remake/research/findings/RE-SAN9PK-0111.md)。

### “开垦最低政治”与探索最低政治实际写入同一地址

两个恢复字段分别名为`CultivateMinPoliticsAddr`和`SearchMinPoliticsAddr`，但值都是`0x4B6787`。安装时先写35，随后写60，最终有效值为60。

原版主库确认该地址属于`0x4B6730`自动探索执行者选择：以人物当前有效政治为下界筛选，再按政治排序；原下界为45。它不是开垦命令效果公式，也不是所有内政的通用政治门。交互探索不经过这条AI选择门。

因此应记录**自动探索最低有效政治45→60**，而不是两项独立改动“开垦45→35、探索35→60”。证据见[字段初始化](../src/generated/StateConstants.inc)、[先写35](../src/runtime/RuntimeInjection2026.cpp:990)、[后写60](../src/runtime/RuntimeInjection2026.cpp:1011)及原版`0x4B6730 → 0x4714D0`。

### 玩家结束操作后，自动安排剩余人物执行有限工作

旧版帮助描述：“玩家战略面操作结束后，剩余的闲置武将由电脑自动安排执行内政”。2019年7月更新说明又为“玩家自动内政”增加训练。当前2026年实现有独立开关，实际工作范围还包括探索和夺取，不能仅按选项名称理解为商业、开垦等内政。

开启后，玩家仍先手动安排本旬命令；点击“进行”、结束当前军团操作时，伴侣临时撤下该军团的玩家直接控制标志，设置自动内政标记，先不推进势力行动游标，让同一军团进入一轮受限的电脑行动。完成后恢复玩家控制，再切换到下一个军团。它不是后台持续检查闲置武将，也不是开局或读档后立即执行。

普通剧本流程使用的专用工作表依次为训练、修筑、商业、开垦、巡察、探索、夺取，对应工作码`5、3、1、2、0、23、31`。这是尝试顺序，不保证每项出令；前项使用的人物、资金及据点工作机会会影响后项。训练排在第一项，不是其他内政做完后才使用最后剩下的人物。表内没有征兵、褒奖、登用、出征、运输或外交，也不会再接普通电脑的末批工作63“剩余人员探索／训练”。

选人和执行复用电脑自动规划器及公共命令。公共筛选排除已经占用行动的人物，各工作再按能力、地点、目标及任务条件筛选；手动命令在先，但剩余闲置人物不保证全部获得任务。有些工作包含逐人概率选择，可能无人入选；实际命令仍消耗正常资源并占用人物行动，不是免费增加内政值。混乱、交战等受阻据点也不能直接作为正常内政来源。

训练复用工作5：来源通过公共状态检查后，还要求本旬训练机会未用、士气低于100、有兵且有可行动人物。选人按武力相关评分排序并作概率筛选，一次最多五人，也可能无人入选。玩家手动训练过或士气已满时，该据点不会再生成同类训练命令；符合条件时，训练会先于修筑、商业等工作取得人物。

探索和夺取确实接入各自的自动任务工厂，仍须通过工作时机、候选目标、执行者及最终命令验证，不能理解为每旬必定派人。这里的夺取是计略夺取，不是褒奖或收取收入。当前专用表没有普通登用工作24，也没有把所有剩余人物逐一派去探索的兜底循环。

这项功能与普通委任军团不同：前者在玩家手动操作结束后补做有限工作，后者本来就走电脑行动流程，工作范围受策略和方针影响。自动内政沿用的父任务仍先准备战略状态及人员配额；配额准备本身不提交武将调动命令，不能据此认定它会替玩家调将。

代码核对：开关`PlayerAutoProcessEnabled`控制`0x50ECDC`处的调用替换，伴侣`0x428B28`在推进游标前切换并恢复控制标志。`0x4BDD8E`接入`0x428B88`，识别自动内政标记后，给父任务写入工作表`0x65776C`、数量7和批次索引2；父任务消费后索引推进到3，普通军团分支不再追加后续批次。原版工厂`0x4BD030`将23／31分别映射为探索／夺取；`0x4BDBD0`负责批前准备，人物可行动筛选经`0x4AF6C0`，训练来源及专属条件经`0x4AE240`／`0x4AE0A0`。以上已核对当前注入代码、工作表和原版调用链，尚未实机验证各项实际出令。

### 避免仕年压过智力，选错电脑军师

更新记录原文：“修复武将仕年导致电脑军师设置错误的问题。”（2025年12月）

原版用“当前有效智力＋仕年加成”给军师候选人评分，仕年最多加10分。例如，智力90、仕年10年的武将得100分，会超过智力99、刚加入的武将。

优化后改为智力优先，智力相同时再比较仕年。实现上将智力放在评分的高位、仕年加成放在低位，避免资历抵消智力差距。这与“军师准确判断的智力=110”设置是两项不同的改动。

### 任官评分与资格

2026替换的是三个独立评分指针。下式L/I/P分别为**基础**统率/智力/政治，T为对应能力的宝物加成，R为义理，D为与根势力君主的相性距离：

| 阶段 | 2026候选分数，降序 | 原版被替换的内容 |
| --- | --- | --- |
| 皇帝特殊官职，编号0—3 | `L + I + T_L + T_I` | 有效统率＋有效智力＋仕年＋忠诚≥150时5分 |
| 武官 | `2×(L + T_L) + R − floor(D/2)` | 有效统率＋仕年＋上述忠诚项 |
| 文官 | `I + P + T_I + T_P` | 有效智力＋有效政治＋仕年＋上述忠诚项 |

`0x44D490`对同一能力的多个宝物取最大加成，不求和。特殊官/文官助手还从调用后的栈下方读取另一个能力的宝物结果；对照原函数局部布局，分别就是智力/政治结果，不能误判为随机分数。此处记录当前二进制行为；未来源码实现应显式返回四项加成，不复刻跨栈帧取数。

任官准备`0x4B2F10`收集同根人物与可授官职。伴侣助手调用原官职收集器后，按尾节点删除官职池一项，没有按编号验证；这里不把“删尾”泛化成可配置官职表下也始终删除某固定官职。然后取得同根总资金F与下次季度前俸禄预留Q：**仅F>3Q继续**，否则清空官职表，后续不能生成正常分配。

资金门通过后，按当前官职编号和类别处理原始人物池：

- 编号>0且属于军事类别1：忠诚<80时直接写人物当前官职为−1，并从池中删除；≥80保留。
- 编号>0且不属于类别1：这道忠诚门不剔除。
- 编号≤0：忠诚<85时剔除，否则保留。编号0也进入此分支，不能简写成“所有现任只需80”。

这是**准备阶段直接改当前官职**的副作用，不等到任官命令验证/提交。另一个助手使据点嵌入驻军中的人物不再提前占用官职池，其他人物仍经原取官职函数保留其占位；后续身份和任官资格仍由原工作14谓词筛选。内层“过滤后人数不同”返回0时保留已填列表，外层`0x4B30E0`不读取此返回值；不能据此宣布普通任官全部失败。

证据：[特殊官评分](../recovery/evidence/payload_disassembly/00421F00_000A1DE0_1E.asm)、[武官评分](../recovery/evidence/payload_disassembly/00421F40_000A0BC0_3F.asm)、[文官评分](../recovery/evidence/payload_disassembly/00422130_000A1CC0_1E.asm)、[资金忠诚门](../recovery/evidence/payload_disassembly/00421DD8_000A1B40_A7.asm)；种子`0x42F7E8`两项载荷在`0x46B462/0x46B923`组成官职占位助手。原版主库`0x44D490`、`0x443010`、`0x4430A0`、`0x44F610`、`0x4B2F10`及`0x4B30E0`。

### 职位分配与计划清理

完整顺序为：君主爵位为皇帝时先配编号0—3特殊官，再武官，最后文官。职位分类不是按官职名称，也不再是原版容量/能力增量判定：编号<4为类别0；其余取`q=(编号−4)>>2`，q<16且为奇数时类别2，其他为类别1。因而4—67按四个一组交替，68及以后走类别1；分类器本身不验证“无官职”等特殊编号。

武官职位按类别1优先、`77−编号`降序；文官按类别2优先、同一排序量降序。助手将类别写入官职`+8`作临时标记，**安装器同时将原循环读取偏移改为+8**，才使两端匹配。人物门也有直接操作数修改：

| 阶段 | 人物门 | 未通过时 |
| --- | --- | --- |
| 武官 | 基础统率≥60 | 结束整个武官阶段，不再尝试后续人物 |
| 文官 | max(基础智力,基础政治)≥70 | 结束整个文官阶段，不再尝试后续人物 |

军职评分排序后，基础统率≥60且基础智力−基础统率≥8者移到临时表；文官排序前归还。文官前原有“直属军团资金>原俸禄预留”判断被助手返回−1绕过，不能把它与[任官评分与资格](#companion-audit-43)同根F>3Q资金门重复计算。

军事和文职选人先查看队首，成功登记计划后才消费人物；因此不合格的武官队首仍可参与后续文官排序。特殊官助手另消费职位队首，避免特殊职位继续留在待分配表中。计划收尾先删除“计划官职等于当前官职”的条目，再检查尚未分配的人物：已有官职且该官职不在剩余职位表中时，追加编号76的无官职计划。它不是所有落选者无条件撤职；收尾助手仅在原计划已非空的构造命令路径调用。

### 俘虏赎金与宝物交换门槛

赎金公共估价`0x48F570`取目标最高两项有效能力的整数平均M，原平方项约为`M²/4`；伴侣在`0x48F5F2`将其提高到约`M²/3`，最低500及`8×(使者政治+势力关系值)`扣项保留。正常正整数范围内，载荷的截断使新平方项为`floor((M²-1)/3)`，不是可以任意改写成浮点的精确4/3倍。另有界面助手重新调用公共估价作为默认金额。

宝物路径改的是**是否接受赎回报价**：原条件`宝物忠诚增量L < min(29,赎金估价/100)`，改为`L+6 < min(29,赎金估价/100)`。因此通常需要多出约600的估价空间，L≥23的宝物无法通过这个严格门。它不是所有宝物交易统一涨价，也不是探索宝物价值变化。

原版本来就有资金可支付额、俸禄预留、宝物价值等拒绝条件；不能把“电脑可以拒绝交还俘虏”全算作新增能力。伴侣能确认的新增差异应落在本节这些具体门槛上。

### 人员配额与压力权重

`BeforeGo`和`0xA0F80`共同生成按据点索引的压力字节：收集有效、未被相关标志排除、以该据点为攻击/当前接战目标的部队；也识别原攻击目标仍为该据点、当前暂与其守军交战且几何距离小于40的情形。对集合求士兵数之和，取`min(255, 总兵数 >> 10)`。它是按1024兵分档的压力，不是敌队数量，也不是直接复用反击留守的攻城损失估计。

另发现一个静态边界：旬前清零192个压力字节，却遍历250个据点编号；高编号没有新压力时的残留风险不能被“每旬全部清零”掩盖。这里只记录边界，不在重制中复制这种数组布局。

<a id="chaos-targets"></a>
## 战略目标与难度偏置

电脑乱战系数影响额外进攻目标的势力筛选，主要是是否偏离指定对手、另打其他电脑势力。不是兵法“混乱”的概率或战斗伤害系数。

在[目标资格包装](../recovery/evidence/payload_disassembly/00423230_000A39B0_29.asm)先通过既有战略敌对检查后，[目标势力过滤](../recovery/evidence/payload_disassembly/00423288_000A2080_7F.asm)对玩家目标及指定专攻势力保留通过；其他电脑目标要求关系值`R < 60`，再以随机门筛选。令`D = 60 - R`、`H = 军团负责人野心`，正常数值范围内的随机阈值为：

```text
参数0： floor(D / 2) + 7 × max(H - 5, 0)
参数c为1～9： (D × 16) >> (10 - c)
```

因此提高1～9档会增加对其他电脑势力分心出兵的可能，不是直接提高攻打玩家的概率；0也不是关闭乱战。[当前写入](../src/runtime/RuntimeInjection2026.cpp:1110)对非零参数保存`10-c`，载荷又将保存值0解释为野心分支，故**参数10与参数0会走同一分支**。该分支与旧帮助“1～10越大越乱战”的描述有边界差异；界面字段允许范围为0～10，见[参数定义](../src/generated/parameter_fields.inc:51)。

### 按君主／都督性格调整自动进攻的兵力门槛

旧版帮助原文：“君主/都督的性格影响发动进攻的条件”。当前实现修改自动出征规划中的兵力强度检查：君主直属军团读取君主性格，其他军团读取都督性格；两者不叠加，也不读取本次出征主将性格。它不限制玩家手动出征，不改变普通攻击伤害或兵法发动率。

令U为规划器从候选来源兵力中扣除留守需求后的可用余量，D为规划器对目标的兵力估值，通常要求`U > floor(D × 比例 / 100)`。比较为严格大于，恰好相等不通过；U不是据点总兵力，D也不能一概替换为目标界面显示的驻兵。性格码0～3依次为莽撞、刚胆、冷静、慎重。

| 当前军团负责人性格 | 普通分组 | 战略优待组 |
| --- | --- | --- |
| 莽撞 | 115% | 140% |
| 刚胆 | 125% | 150% |
| 冷静 | 135% | 160% |
| 慎重 | 145% | 170% |

原版对应两组固定使用125%／150%，这段检查不读性格。伴侣改为基础115%，战略优待组通常另加25个百分点，再按性格码增加0／10／20／30个百分点。因此刚胆保留原门槛，莽撞降低10个百分点，冷静、慎重分别提高10、20个百分点。例如D为40000，普通组莽撞要求U严格大于46000，慎重要求严格大于58000；通过后仍须完成选人、兵力分配及最终命令验证，不保证一定出征。

战略优待组对应原版AI元数据bit7，行动收敛组对应bit8，均为战略分组，不是人物性格或难度。“战略优待组”概括部分敌对计略／在职登用规划会回避该组的行为，并不表示更容易进攻；该组原本还影响城市／关的留守需求估值。行动收敛组减少工作尝试及部分规划机会，不能只理解为兵力较弱。这些名称为本项目按用途归纳，未确认是原作正式术语。

伴侣还修改了势力数量减少时的分组处理：战略分组更新时，若普通电脑主势力不足4家，不计玩家、异民族及附属军团，便将普通电脑主势力和异民族全部置入战略优待组，并把该组额外比例从25个百分点降到10个百分点。更新到此分支后，莽撞／刚胆／冷静／慎重的门槛分别为125%／135%／145%／155%。这不是势力灭亡瞬间立刻重算，也不能把判定数量误写为包含玩家的全部势力数；原版相应数量门包含玩家。

性格比例有提前绕过的路径：攻击本联盟讨伐目标使用75%门槛，吕布为君主的特例使用100%门槛，均先于性格补丁；目标没有有效所属势力时，该强度检查直接通过。调用方还可能因已有合资格协同进攻部队而跳过整段检查。普通分组比例不通过时，仍保留根bit8成立且来源总兵力至少70000时，按君主野心加5判概率的后备机会；这里读取根君主野心，与都督性格分开。战略优待组比例不通过则直接失败，不进入该后备骰。

2019年与2026年的性格及数量配套补丁代码、挂钩地址相同，未发现规则变化。当前随基础补丁安装，没有独立开关；它与部队主将性格影响接敌、追击或自主撤退是不同层次的机制。

代码核对：原版进攻强度检查入口为`0x4B57F0`，`0x4B5AF4`跳入伴侣`0x426040`的53字节缓冲区，读取规划器`+0x38`的当前军团、军团`+0xBC`的直属负责人及人物`+0x78`性格，计算比例后分别返回`0x4B5AAA`／`0x4B5B06`继续除100和严格比较。`0x4BE443`接入`0x427940`的数量处理缓冲区，少于4家时置组，并改写性格缓冲区基准注入地址`0xA59C7`处的额外比例掩码为10，否则写25。根分组读取经`0x4AF5A0`／`0x4AF5F0`，后者的后备骰仍读取人物`+0x74`野心。以上已与2019年源代码及san9-remake的原版AI权威研究核对，尚未实机验证进攻结果；`0xAxxxx`为会重定位的基准注入地址。

<a id="sortie-allocation"></a>
#### 普通出征分兵

两个出征路径替换实际兵量选择，在主将带兵容量大于10000、可分配兵量至少20000、候选人物足够等条件下进入再分配。

- 先按15000分组：`组数 = floor(可分配兵量 / 15000) + (余数 >= 10000 ? 1 : 0)`，再受可用人物数限制。都市/关类分支还会先扣除一个人物名额。
- 按组数计算平均兵量。遍历主将容量；对容量低于平均值的主将先扣去其可带兵量，再为剩余队伍重新计算平均。
- 一条路径还读取已经安排的组数，避免用最初的总组数重复分配。两条入口上下文不同，不能合成不带前提的“全AI统一15000人”规则。

例如可用兵45000且有3个合适主将，初始平均15000；若其中一人容量只有12000，算法会继续以剩余33000兵、2组重新分配。这比“主将都尽量带满，最后一队吃余数”多了一层均衡。

**证据：**[出征分配一](../recovery/evidence/payload_disassembly/00425D88_000A5800_EA.asm)、[出征分配二](../recovery/evidence/payload_disassembly/00425EA0_000A5900_BD.asm)，路径分别为`0x004B4C03 → 0x000A5800`、`0x004B4E3E → 0x000A5900`；[安装入口](../src/runtime/RuntimeInjection2026.cpp:785)。两段均调用`0x44D700`查询主将带兵容量。

### 初始设施候选与续攻估值

**初始进攻不是把所有目标按距离一次排序。**原版`0x4B6190`已有分阶段候选流程，伴侣另外插入群攻玩家、机会空城等分支；来源资格、战略对手、兵力和人物仍须通过各自的门。2025年12月“优先考虑接壤设施”的对应常驻改写已找到：`0x42CE38`挂接`0x4B5C28 → 0xAA600`，在普通设施候选的既有敌对判断成功后，进一步检查目标地域是否邻接本根势力所属建筑。`0x435A20`使用地域邻接链，区别于军事邻城表、直线距离及路线长短。

在这条路径中，它实际加强了**已占领敌设施的候选资格**，不能只描述成排序分数加权。原“未占领设施”后备仍保留；随后仍执行原估值排序，估值助手也有另一处改写。设计意图是先处理有己方前沿接触的据点，减少跨越前线选择难以持续支援的敌设施，并不表示所有城市、请求出兵或事后攻击统一受这一个门控制。

**续攻按同一目标聚合兵力。**`0xA2B00`收集正在威胁该目标的队伍，`0xA00F0`判断是否继续：进攻量对部分陆上长蛇队减半计权；防守侧汇总目标现兵、回归兵和正在针对这组来攻队伍交战/进军的野外兵力。常态门为进攻量严格大于防守量的`44/64`；守军不多且已交战时有保留进攻的例外。这里不证明双方都按同一势力或精确战斗力归一化。设计意图是避免一队单独因兵少撤退，也避免整批部队在局势转坏后继续添油；通过时再安排[旬前协同改阵与等待](#companion-audit-54)护卫与出发协同，失败时走[回撤目的地与容量](#companion-audit-59)回撤。

证据：[接壤候选助手](../recovery/evidence/payload_disassembly/0042CD8C_000AA600_86.asm)、常驻描述符`0x42CE38/0x42CE44`；主库`0x4B5B60/0x435A20`确认调用位置及地域集合；[续攻入口](../recovery/evidence/payload_disassembly/00421530_000A2B00_A2.asm)、[续攻门](../recovery/evidence/payload_disassembly/00422B60_000A00F0_4D.asm)、[长蛇折算](../recovery/evidence/payload_disassembly/00422BB0_000A3600_3C.asm)、[野外防守量](../recovery/evidence/payload_disassembly/00422BEC_000A0200_A2.asm)。

### 反击留守估计

依据为`0x426758 → 0xA6000`的779字节载荷、权重助手`0x426A64 → 0xA3100`，并以原版主库核对被调用函数。以下数学表达限定正常数值范围；低字节运算、每步截断及定点乘法不能合并成一个浮点公式。

**留守预算边界。**敌军列表非空时，先取`U = min(30000, 本城现兵, 3000 + 5000×敌队数)`；累计值从3000开始，最后返回`max(6000, min(累计值, U))`。调用方另要求扣除此留守后至少还有6000兵可出。

**可形成压力的时间。**设基础到达时间为路线天数减2，城市再减1，下界取0。伪装状态4加两倍状态剩余日数，混乱状态6加一倍；尚未接近且时间大于1、单位标志命中`0x400004`时再乘2。用本旬剩余日数减去该时间；无阵状态5还要扣除到达后尚未消退的无阵时间。剩余攻击时间不为正则跳过该队。

这里的状态4是EXE文本“伪装”（由伪报命令产生），状态5是“无阵”，不是陷阱；`0x44CD00`是人物阵位所在排，不能误写为性格或兵法发动率。原版字段依据见[状态研究](../../remake/research/findings/RE-SAN9PK-0029.md)和[人物研究](../../remake/research/findings/RE-SAN9PK-0009.md)。

**普攻部分。**先由己方战力、内嵌驻军的阵形参数、耐久打包字和原攻城系数构造防守项`F`；敌方以战力和适用陆/水阵形参数构造差值`X = 2×敌战力×阵形参数/25 - F + 900`。再以`X² >> 11`、敌兵与U之和、攻击时间t计算累加量，结构为：

```text
t × [ ((X² >> 11) × (400 + (敌兵 + U) × (44 - t) / 3150)) / 600 ]
```

每步均沿用原整数截断。己方F的耐久项直接使用`建筑+0x3C`低字及`0x49A446`处系数，不能把这个打包字直接替换成任意现代模型的“耐久值”而宣称等价。港口且敌队满足水军条件时，选用水阵；其余用陆阵。

**兵法部分。**对该队每个人物，结合伤势计数`+0x80`与兵法冷却`+0x98`，计算到达后本旬还可能施法的时间；并受前述可攻击时间限制。普通路径只考虑当前装备且可作用于设施的兵法。水军路径另按船型映射31/32号兵法；不满足相应船型时，只放行类别7/8的适用兵法。

物理类别用武力、其他类别用智力，经执行能力变换后取`max(变换值+45,70)`，再乘`熟练度/2+1000`、兵法威力和可用时间。非水军类别再乘`(4-人物所在排)/40`；水军不走这一步。物理威力取兵法记录，智力兵法ID23—30使用专用权重`7/12/10/15/5/5/12/15`，它由伴侣写到`0x45D8E7`，不是原版该地址原有的数据表。

最后的定点权重约为：水军0.8；特定兵法类别与陆阵匹配时1.0；其他0.5。每支敌队的兵法附加量最多8000。此处是AI的威胁估算，不能用它替换实际兵法伤害结算。

**反编译边界。**在独立研究副本中装入载荷辅助反编译，随后逐分支回读汇编。原版主库没有被写入伴侣程序字节。反编译器会把原游戏代码区中的伴侣运行时变量错误折为常数，还会错误恢复定点乘法和部分寄存器传参；本节以载荷指令为准，未进行原游戏战役实验。

### 预警与留兵条件

`0xA3D00`枚举据点关联的城市对象，按是否同君主分别记录最小几何距离；实际返回路径只使用非同君主的最小距离。距离不大于80时返回2，否则返回0。

载荷中本拟返回1的分支再次比较了同一个寄存器，未使用已计算的同方距离，因此正常入口下**返回1不可达**。它没有读取玩家中继命令，也没有预测玩家下一步操作。“防中继点战术”是旧帮助对策略效果的概括，不能当作这段函数的输入定义。

已确认的消费者包括：非城市来源原留兵低于4999时，预警值2将保留门提高到4999；无预警且原留兵为0时至少留1。若它是军团唯一相关城市所辖的该设施，还会先走留1的例外。另有反击来源过滤及预警标记写入消费者，不能把返回值直接当兵量。

证据：[预警载荷](../recovery/evidence/payload_disassembly/004233A8_000A3D00_81.asm)、[留兵消费者](../recovery/evidence/payload_disassembly/00420ED0_000A0450_8B.asm)、[来源筛选](../recovery/evidence/payload_disassembly/00422760_000A33C8_31.asm)、[标记写入](../recovery/evidence/payload_disassembly/0042342C_000A3D90_3E.asm)。这是2026实际分支，不能用旧帮助“孤立设施留0/1、邻城留6000”的几个数概括所有路径。

### 反击编队与人物角色

`0x4A3BB0`先按原主将优先级选第一人，其余按与此人相性距离排序。2026在`0x4A3D00`用`pop/pop/jmp`替代原追加队员调用，保留剩余人物供新助手消费；遗漏这个直接写入就会误以为原队员已选完。以下P为**主将弹出后**的剩余候选数，不是出发前总人数；上游普通路径至少两名候选，P≥1。B为驻兵减本次缓存留守估值。

| B范围 | 名义分组数与本队兵量 |
| --- | --- |
| <6000 | 交还原尾部，最终不足6000拒绝 |
| 6000—15999，且B≥12000、P≠1 | 2组，本队`floor(B/2)` |
| 同范围其他情况 | 1组；B≥10000减1000，另在P=1且B≥13000时再减1000 |
| ≥16000 | 从h=8000起，每次加2000，算`n=floor(B/h)`；P≥n时采用，否则继续，最多试h=20000；本队`floor(B/n)` |

例：B=12000、P=1给11000；同兵量P=2给6000。B=13000、P=1给11000。大兵量路径到20000档仍不匹配时直接使用最后的n，**没有再做n≤P的硬截断**；名义分组数不保证后续实际能出齐。返回原尾部后仍取`min(本队计算量,主将带兵上限,25000)`并要求≥6000，不能把表内数值直接当最终出兵。

本队目标人数先按`clamp(floor(P/n),1,4)`计算，再扣已选主将得到副将槽；有余数且未满4人时，还可能从剩余队首补一名与当前参考人物相性距离≤3者。余数不是无条件补满。

智力型分类助手返回非零的条件为：有效智力>80；或基础智力−基础武力≥8且（有效智力≥70或会教谕22）。配额由此类总人数除n计算，一般向上取整并封顶2，再扣已选主将的类别、受副将槽限制。城市自指且`+0x51==0`时有特殊取整：商为1直接保留1，商为2且整除时降为1；商2有余数时仍保留2。此字段的玩法命名尚未进一步确认，保留精确条件，不编造性格含义。

选择副将前重新按原主将优先级收集人物，将名义n组对应的前n人从临时副将表排除，为后续主将留人（其中可能包含刚选的当前主将）。随后按配额取智力型人物；扫描中**所有智力型都会从本队临时剩余表删除**，未入选者留给其他编队重新收集，不是永久删除人物。其余槽先按相性距离≤3及相邻相性连串分配，装不下时继续后探，末尾还有取队首的后备。这里没有保证全部成员与最初主将两两相性≤3。

证据：[分组主载荷](../recovery/evidence/payload_disassembly/004206A8_000A0800_1A1.asm)、[预留主将](../recovery/evidence/payload_disassembly/00420878_000A09A8_4F.asm)、[相性与余数](../recovery/evidence/payload_disassembly/004208C8_000A1A00_C7.asm)、[智力分类](../recovery/evidence/payload_disassembly/00420990_000A6490_2E.asm)；常驻字段6504/6508把`0x4A3D00`改为`58 58 EB 01`。原版主库`0x4A3BB0`、`0x4A1600`和容量尾部`0x4A3DD8`；留守估值另见[反击留守估计](#companion-audit-27)及设计说明反击留守。

### 单人后备选将

`0x4A3E90`的Group2单人派兵/后备路径替换了取队首调用，它与[反击编队与人物角色](#companion-audit-47)主反击多人编队不是同一入口。输入已由`0x4A1600`按主将优先级降序排好：

- 候选≥5：从**队尾向前**扫描，遇到有效智力≥64即选；均不达标时取最高智力，同分保留此次扫描先遇者。代码用有符号字节比较，64解释限定正常能力范围，不承诺修改后超127属性仍按整数大小运行。
- 候选<5：从队首向后扫描。资格助手接受“有效武力≥60或智力≥65或政治≥60或统率≥65”。通过者按`max(有效武力,有效智力,有效统率)`最小优先，同分保留在前者，政治只用于资格。

但第二支的**不通过分支不是跳过**：`0xA05A9`跳`0xA05D9`，只要当前节点非空就继续`0xA05DF`返回当前人物。因此遇到首个不合格者立即终止，即使之前已有更低评分合格者也会被覆盖；后续人员不再扫描。只有全部候选均通过、链表走到末尾时，才返回积累的最佳节点。

例如队列A/B/C，A有效能力(武70,智70,政70,统70)，B四项50，C四项65：代码选B，而不是A或C。此例是按指令分支复核的边界推演，没有运行原游戏证明实际现场频率；上游可行动人物收集本身不能当成“四项至少一项过线”的保证。该助手返回人物时不消费原节点，随后临时表销毁，不能把这点直接计为重复派遣漏洞。

证据：[单人助手](../recovery/evidence/payload_disassembly/004201FC_000A0560_86.asm)及`0x4A3F08`挂接；种子`0x42F6C0`三项载荷把资格助手拆放在`0x46EFB2`、`0x46EF75`、`0x46EF25`，必须拼接分支后阅读。原版主库`0x4A3E90`、`0x4A1600`、`0x4AF900`与`0x4AF840`。

### 智力兵法能力分档与概率

共同助手`0xA2DE0`把人物分成三档，令B为基础智力、W为基础武力：

| 返回档位 | 精确条件 |
| --- | --- |
| 1 | B−W≥8且B<80 |
| 2 | B−W≥8且80≤B<90 |
| 0 | 其余，包括B≥90 |

这是基础智武差与基础智力分档，不是“智力越高越优先教谕”的单调评分。该档位被普通进攻与反击的不同助手消费，不能直接解释成通用武将职业。

另有两处常驻改动，把对应AI选法概率中的`2×(当前智力−当前武力)`改为`8×(当前智力−当前武力)`。普通进攻还把`0x4B8295`的跳转位移37改0，取消“没有弓骑/弩兵候选就免过概率”的旧旁路；不是给所有兵法增加同一发动率。

反击改动替换了“左移＋存概率”的整段：助手`0x453911`把8倍差值直接写回调用者概率槽，返回后的`inc eax`不再存回，因此**实际概率槽不是8倍差值再加1**。普通进攻的`0x4538B6`则重排调用栈，把8倍差值交给原公共概率函数。两处属于选择兵法时的随机门，不是战斗发动率或最终效果倍率。

证据：[分档](../recovery/evidence/payload_disassembly/00423EA8_000A2DE0_1E.asm)、[反击概率存槽](../recovery/evidence/payload_disassembly/004215D8_00453911_8.asm)、[反击挂接](../recovery/evidence/payload_disassembly/004215E0_004A1BB9_6.asm)、[普通进攻概率栈](../recovery/evidence/payload_disassembly/0042160C_004538B6_9.asm)、[普通进攻挂接](../recovery/evidence/payload_disassembly/00421618_004B82A5_5.asm)及常驻字段`SelectCleverKiller`。原版主库`0x4A1930`与`0x4B7C60`。

### 普通进攻与反击的兵法选择

本节兵法编号采用实际记录：21破陷、22教谕、23混乱、24陷阱、25攻心、26幻术、27辱骂、28鼓舞、29治疗、30妖术。不能把23/24互换。人物能力、兵法合法性收集及特殊30/26/29的先行随机选择仍有上游约束，以下是对应分支到达后的差异。

**普通进攻9/59，`0x4B7C60`：**

- 在原沿水路/港目标分支，将`0x4B801D`的条件跳转改为无条件跳转，跳过破陷21的提前优先。其他后备仍可能选到破陷，不是全局禁止装备。
- 教谕22的该处去重检查保留；未重复时，[智力兵法能力分档与概率](#companion-audit-49)档位1允许提前选它，档位0跳过，档位2另过50%随机门。
- 普通受限候选原先由混乱23、攻心25及教谕22组成。轮到追加教谕时，档位1先清表再追加，使其独占这张临时表；档位2正常追加；档位0不追加，原表非空就保留原表，空表则转后备。该路径仍须通过前面的8倍智武差概率及计划去重门，不能说档位1无条件选教谕。
- 没有弓骑/弩兵而转入后备时，新助手先在攻心可用时加入攻心，否则在混乱可用时加入混乱，并跳过原破陷/陷阱的部分追加；后续辱骂、鼓舞及原比较/并入流程仍在。不能把这个后备概括为“只剩辅助兵法”。

**防守反击58，`0x4A1930`：**

- 在取出混乱23、辱骂27的候选标志时，另比较`当前智力−当前武力 > 剩余物理候选的最大威力M`。严格大于才保留该项；没有物理候选、M=0时仍要求智力高于武力。载荷里先写的“无物理候选”布尔值随即被`setg`覆盖，不能误读为无物理兵法就无条件放行。
- 破陷21提前分支仍要求目标实际装备陷阱24、本计划未重复。档位0跳过，档位1允许，档位2仅在自己没有可用陷阱24时允许。
- 教谕22提前分支的目标检查中，原来最后测试陷阱24的调用改为妖术30；结合其他原检查，目标实际装备混乱23、攻心25、幻术26或妖术30可以进入后续判断。读取的是目标当前装备，不是其已学集合。

### 事后选敌的路线评分

原版`0x467190`在旧目标失效后收集候选部队，逐个调用`0x45EE80 → 0x45EDF0`写排序量，再升序取首。原助手虽求过路径及几何量，最终却`xor eax,eax`返回0；不能把它描述成原本已经按实际路程稳定排序。

2026常驻三段改写从路线表取节点数L，并改为返回该值；无参数或无正长度路线时返回`0x7FFFFFFF`，使其排到后面。正常路径还进入`0xA2400`：从调用栈中的保存对象验证地图对象引用，并要求它当前地图格与路径目标格相同。**上下文匹配时**扫描路线格，使用`0x45D070`检查实际穿过的建筑矩形：遇到归并类型7—10的工作物，或对参考地图对象满足原敌对谓词的建筑，则设置惩罚位。

匹配分支的返回评分为`(L | (有惩罚 ? 0x20000 : 0)) << 12`，正常长度范围内惩罚表现为额外`0x20000000`。比较的是排序等级与路线节点数，不是实际行军日数，也不是只要经过敌方地域就罚。上下文验证不匹配时助手直接保留原L，不能把移位与惩罚扩大为该共享函数所有调用的统一公式。没有重新填充原本为空的建筑候选表，也不能凭旧代码中的建筑后备分支宣称这里新增了通用事后攻城。

这个共享排序写入器另被转属后的动作重选路径调用；当前结论限定于已追到的调用与上下文门。目标候选、策略许可、性格/强度裁决仍另行作用，不等于总会攻击评分最低者。

证据：常驻描述符`0x42CD40`起三项，改`0x45EE1B/0x45EE3B/0x45EE63`；来源`0x42CD04/0x42CD0C/0x42CD34`；[穿越评分助手](../recovery/evidence/payload_disassembly/0042CC90_000A2400_72.asm)。原版主库`0x45EDF0`、`0x45ED70`、`0x45EE80`、`0x467190`、`0x45D070`及`0x435440`；后两者分别确认实际矩形穿越及归并类别，不以地域归属替代。

### 旬前协同改阵与等待

旬前入口`0x50F16E → 0xA1000`先调用原军团游标。游标耗尽时才统一进入`0xA2B00`续攻检查；其中一条继续进攻的通过分支调用`0xA6600`，使用已收集的同目标部队表，不是任意日期对全世界所有军队执行。

**改编队范围与数量。**全表至少两队才继续；过滤已经每日处理的单位bit3、所属军团自身带玩家/异民族位的队伍及陆阵长蛇6，然后按**直属军团**分组，取根势力兵法位集。设某组总队数N、未置单位`0x1000`位的队数U：N>2时最多改`max(0,U−floor(2N/3))`队，否则最多U队。已有该位的队伍排序量置为最小有符号值，通常排后，不是全部都改成一种阵型。

对未跳过者，分别估算鱼鳞0、锥形2、箕形5：仅当前装备物理兵法（类别0—3）的人物进入兵法收益估算及替换，从其可用编号0—11兵法中挑分数最大者；对应优先区间分别为0—2、3—8、6—11，区间外威力先除2，同分取较高编号。三阵总分同分时优先0，再2，再5；再减去当前已装备物理兵法的阵形适配分形成队伍收益，按收益降序选队。**数量预算确定后，没有再要求被选队伍收益>0。**当前项使用固定点乘法的高32位再乘2，保留其截断，不是直接使用浮点倍率。

选中后直接写场上人物当前物理兵法、阵位和单位陆阵，并置`0x1000`。这个位也是原“敌接近时攻击”方针位，不能只解释成内部“已处理”标记。助手本身不经过公共变阵命令及其费用验证；原出阵时的合法性也不能自动证明这次直接调整的全部条件。玩家目标还会进入额外特殊陆阵尝试，完整采用判断不在此通用三阵评分内。

**等待计算。**其后`0xA5D40`只在该组N>1时处理，并跳过已置`0x1000`者。对其余队伍取到同一目标的路线ETA t：

```text
a = floor(参与求和的ETA总和 / N)
h = a + floor(floor(参与求和的|t−a|总和 / N) / 2)
每队出发等待 = clamp(h−t, 0, 9)
```

分母是组内总数N，**不是实际参与求和的队数**，被跳过者仍影响分母。t=4/12、N=2时等待6/0；t=4/20时等待9/0，因9日封顶并不能完全同步到达。写入的是部队`+0x48`出发等待，不是人物行程计数或本旬第几天出发。

证据：[入口](../recovery/evidence/payload_disassembly/00421230_000A1000_2D4.asm)、[续攻调用](../recovery/evidence/payload_disassembly/00421530_000A2B00_A2.asm)、[通过分支](../recovery/evidence/payload_disassembly/00422B60_000A00F0_4D.asm)、[协同改阵](../recovery/evidence/payload_disassembly/004274C8_000A6600_274.asm)、[逐人适配](../recovery/evidence/payload_disassembly/0042773C_000A6540_6C.asm)、[等待](../recovery/evidence/payload_disassembly/004277A8_000A5D40_B5.asm)。原版主库`0x468870`确认路线ETA，原方针写入`0x45EAB0`确认位`0x1000`；续攻估值与失败回撤见[目标与续攻](#companion-audit-58)、[回撤](#companion-audit-59)。

### 接力需求与中继轮换

接力筹兵与续攻失败回撤是独立流程；回撤见[目的地与容量](#companion-audit-59)。

接力入口是工作58的Group2配对器`0x4A3630`：对一个有兵力缺口的目标A，直接来源集合为空时，在`0x4A3A9E`调用`0xA0300`。**触发条件是找不到直接配对，不是已生成派兵命令执行失败的回调。**开关只把助手`+20`处的跳转改为`75/EB`以允许/跳过登记；来源留兵及运量助手另为常驻安装，不能把关闭接力理解成恢复全部原版留兵规则。

令P(X)为本工作对象的压力表、D(X)为当前伴侣的防御兵量、U(X)为本工作缓存的可外援额度。三者不是同一个“现兵”数：

- 初始Group2候选的P先取符合`0xA0F80`、路线ETA<20的来攻部队士兵和，再限制到`容量−10000`；若D<8000且该值<10000，提升到10000。随后还要P−D>0才加入原始目标表。
- D经`0x4A12A0 → 0xA2550`计算：现驻兵＋服务关联表中原始命令38且目标类型3（部队）的士兵＋命令39/51/52、主目标匹配、没有临时目标且非状态4/6的在途士兵。不计这些队伍的伤兵。该调用临时将`0xA1990`的距离分支改为无条件跳转，故这里的在途数**不限近期到达**；[人员配额与压力权重](#companion-audit-28)常态近期回归兵则仍有限距/ETA门。
- P在接力登记时可以被策略需求覆盖；U由直接救援来源筛选初始化并在生成计划时扣减。

无待处理中继且A不在冷却时，计算缺口`S=P(A)−D(A)`。只有`S≤floor(max(D(A),20000)×11/16)`才尝试中继；缺口过大就放弃这次登记。正常到达此入口的S为正。

按A父城市对应的八项邻城表**原顺序**寻找中继B，不按最近路程、最大驻兵或综合得分排序。B必须满足：

1. 城市引用及所属军团有效，所属根军团等于当前工作军团。
2. 服务人物计数`+E8>0`；这不等于必有可行动人物。
3. U(B)≤0；−1尚未初始化也符合，不限定为恰好零。
4. P(B)≤D(B)，即登记前它自身的压力已能覆盖。

首个合格B得到`P(B)=max(D(B),10000)+S+5000`，由`0x4A1160`**覆盖写入**，不是在原P(B)上累加。载荷中虽计算了`P(B)+8000`，但随后的无条件跳转使该值不参与最终选择，不能据此多加8000。B追加到当前工作目标队列尾，记录全局待处理中继B及原目标A。

随后规划器把B当作需要增援的目标，从其他合格来源向B派兵。若B也找不到直接来源，助手回到**原A的邻城表**，从B之后继续寻找B2；不会从B的邻城继续递归扩展任意多跳。八项用尽就清待处理中继。换城时没有恢复旧B被覆盖的P；压力表随工作对象销毁/新建重置。全局同一时刻只有一项待处理中继，其他目标不能并行登记；预算耗尽本身没有专门清该全局指针，可能使本旬后续工作继续受其非零门限制，下一轮统一准备再清。

例：A的D=10000、P=16000，S=6000，通过13750门；B的D=10000、原P=3000且U≤0，则新P(B)=21000，剩余缺口11000。它不是追加21000，也不是自动预订一条“C到B再到A”的双段命令。登记只促成向B筹兵，B后续能否援A仍由正常规划及实际世界状态决定。

证据：[接力失败/登记载荷](../recovery/evidence/payload_disassembly/00420D10_000A0300_146.asm)、[初始压力修正](../recovery/evidence/payload_disassembly/00421B88_000A2520_2E.asm)、[防御兵量](../recovery/evidence/payload_disassembly/00422AD8_000A2550_5C.asm)、[关联野战兵过滤](../recovery/evidence/payload_disassembly/00421C50_000A1780_34.asm)、[在途兵](../recovery/evidence/payload_disassembly/004218A8_000A1990_6A.asm)。原版主库`0x4A1160/0x4A1190/0x4A1270`确认覆盖写入及缓存语义，`0x4A2FD0`确认初始目标，`0x4A3630`确认失败调用与队列消费。开关写入见[参数安装](../src/runtime/RuntimeInjection2026.cpp:1256)。

### 接力派遣、完成与冷却

**来源和运量。**常驻种子助手在`0x4A37AF`将原直属军团判断改为“来源所属军团有效、自身无玩家位、与当前军团同根”；因此电脑副军团不能自己运行该工作，与主军团能否从同根副军团据点筹兵，是不同权限问题。配对仍要求来源现兵>1000、有可用人物，保留后备压力检查，路线实际穿越工作物或敌对建筑时拒绝，再按合格路线节点数升序选来源。来源和目标的状态门不能相互套用。

城市来源的缓存额度为`max(0,min(G+R−10000,G−1−P))`：G是现兵，R为常态近期回归兵，P为来源压力表。非城市保留原压力/城关最低留兵，再按[预警与留兵条件](#companion-audit-29)预警提高到4999、至少留1；当前军团都市表恰有一城且目标就是该城时，有直接改留1的例外。关类原最低10000不能省略；其他原人物、压力、路线门仍另行作用。

Group2单人计划的选将见[单人后备选将](#companion-audit-48)。原兵量帽是城市/关10000，其他建筑取人物带兵容量，再与剩余额度取min。伴侣新门先检查**剩余额度**：小于3000就将该来源额度清零并返回0；否则正常取min。因此并非所有最终派兵都保证≥3000，低于3000的自定义人物容量仍可能使结果更小。额度在命令构造前就扣除；空命令、公共验证失败及成功提交均消耗尝试预算，失败不自动退还额度，也不自动登记另一条接力。

成功配对会把当前目标及剩余目标回填工作队列，来源可再次使用，没有每个来源/目标组合只能试一次的通用集合。实际派遣走`0x4A4430 → 0x4B9AF0 → 0x4B76B0`的公共派兵命令；并非调用单武将3000兵救援计略。人物、剩余额度和公共命令条件决定还能否继续派。

**完成与冷却。**名叫`codeRelayDispatchOk`的助手实际挂在`0x4A3712`：下一次配对扫描发现当前目标`P−D≤0`，才调用它重置来源额度缓存。若该目标恰为待处理中继B，给原A写冷却2并清待处理中继。它不是“派兵成功立即冷却”回调，不要求兵已到达；D已计入在途援军。若最后一次派兵后预算直接结束，没有下一次扫描，也不能保证当场设冷却。

冷却只阻止为A新建中继需求，不禁止合格的直接救援。递减发生于下一轮统一准备中首个合格NPC根军团入口，每轮对192个字节减1，值0保持0；不是每个军团都减一次。对编号一致的城市，写2意味着随后一次准备为1、再下一次为0。待处理指针在该入口另行清零；压力、额度属于工作对象，冷却则在独立注入区，不能把工作对象重建与冷却重置视为同一件事。

**已确认的设施索引问题。**冷却读端使用建筑虚槽`+0x0C`：城市返回本地编号i，设施返回本地编号j＋50；写端却直接读取对象`+4`低字节，城市写i、设施写j。城市读写一致，设施不一致。冷却区基准`0xA0E00`仅192字节，后方`0xA0EC0`就是上述完成助手：设施j≥142的读地址越过冷却区，j≥192的写地址也越过；例如j=142会读到完成助手首字节`B8`并当成非零冷却。这里确认的是实际索引和代码布局，未以原游戏场景宣称已经复现崩溃。

**与39r插件不能视为逐项等价。**插件`AiPlus.Relay`在`Send`成功后处理冷却/清需求，以在途援军近似原两轮冷却，并用组合集合避免重复尝试；原版则按上述“下次扫描压力已覆盖”判完成、缓存额度控制重复派遣。插件还按近20日压力等近似值选来源，非城市留兵与预警、关类兵量帽也需按实际代码分别判断。功能思路相同，不应再将其概括成完整复刻。

### 回撤目的地与容量

### 运输配对、账目与运量

最终来源助手直接替代原收集器，并修改返回地址跳到`0x4BBE73`。因此原`0x4B04B0`直属军团及查询状态门、`0x4BBB10`人物/士气/兵力门均不再在该处执行；只保留[运输账本与候选资格](#companion-audit-45)的新初筛与末筛。原始驻军状态1与原查询状态1并不等价，交战时尤其不能混称。新来源评分为：

```text
账本值
+ 1000000（容量溢出标记bit3）
+  250000（不是城市）
+  250000（无元数据标记bit6）
```

按该分数降序；目标按账本升序，更负者在前。原配对函数`0x4BC240`遍历来源，每个来源重新置阶段0，并依次扫描：

| 阶段 | 地域要求 | 目标账本 |
| --- | --- | --- |
| 0 | 来源所在城市及其军事邻城 | ≤−6024 |
| 1 | 任意候选城市地域 | ≤−6024 |
| 2 | 与阶段0相同 | >−6024 |
| 3 | 任意候选城市地域 | >−6024 |

所有目标仍须先过<−5000门，不能把阶段2/3读成无条件接收。每次要求路线不被`0x4BB7A0`阻断，成功即消费当前来源与目标；四阶段均失败才试下一来源。邻近按军事邻城表及目标父城市判断，不是直线距离。来源可否保留去扩张空地，也由是否存在≤−6024强目标决定；不能把6024粗写成6000。

原运输选将`0x4BB630`保留，按四项有效能力之和升序，在可行动人物中选低分者。运量按本节三分支计算，而非固定10000或严格填满负数。计划构造时`0x4BB5F0`先从来源账本减N、给目标账本加N；配对列表也被消费，后续配对不会无限重复同一未变账目。非城市被完全搬空时，构造器可走普通派兵后备，其他情形走运输构造；不能把工作51每次成功都说成一定建立相同命令类型。

#### 账目编码

854字节载荷重写每个据点的输送账目，调用另一分类函数区分同势力、普通对手、玩家、空白地域、异民族等情况，并沿路线检查经过建筑、通行和敌对资格。不能只用“后方向前线搬兵”概括。

- 同势力以根军团比较，不只比较直属军团；普通对手分类还读取外交关系，70是其中一个分界。
- 邻境经路线检查后设置不同标记。部分玩家邻境路径按`敌驻军 × (90 - max(路线天数, 20)) / 60`增加部署量，正贡献只在90日以内；也有转入另一标记的分支。
- 其他路径出现50000、20000的保留兵量。是否进入取决于关系类别、路线和已有标记，不能解释成所有边境统一留这些兵。
- 使用`floor(据点容量 × 123 / 128)`约96.1%的容量线，并在相关分支抑制不超过5000等小额流出，体现预留空间和避免零碎调动的倾向。
- 普通对手邻境的一条路径直接写入`-(5000 + 0..1023的扰动)`；部分玩家邻境路径另有负值压低。**负值不总是精确的物理缺兵量，而可能编码接收优先级。**

**证据：**[运输账本载荷](../recovery/evidence/payload_disassembly/00424DF0_000A5000_356.asm)、[邻境关系分类](../recovery/evidence/payload_disassembly/00425198_000A4F00_5B.asm)，主路径`0x004BC0CE → 0x000A5000`；[安装入口](../src/runtime/RuntimeInjection2026.cpp:744)。

#### 单次运量

令`S`为来源输送账目，`D`为目标账目的相反数，`C`为选中人物的带兵容量。正常进入该运量选择路径后，实际分支为：

```text
S <= 10000               → S
S > 10000 且 D <= 10000  → 10000
S > 10000 且 D > 10000   → min(S, D, C)
```

例如`S=50000, D=40000, C=30000`时返回30000；目标账目为`-6000`、来源充足时会返回10000。结合账目的优先级编码可知，它不是严格的“缺多少就送多少”算法。`-3000`只满足孤立运量助手的输入形式，不能通过完整目标门`<−5000`。

运输人物按四项有效能力之和升序选择；计划阶段即从来源账本减去本次兵量、向目标账本加回。它有在途与当前工作计划的部分记账，并非每次从同一未变快照无限派兵；但目标负值混有优先级，仍不等于精确需求消耗。见[运输配对、账目与运量](optimizations.md#companion-audit-46)。

**证据：**[运输载兵载荷](../recovery/evidence/payload_disassembly/00425530_000A5CB0_50.asm)，路径`0x004BB6EC → 0x000A5CB0`；[安装入口](../src/runtime/RuntimeInjection2026.cpp:742)。原位置为一万上限选择，注入路径调用`0x44D700`。

### “降低建筑费用”实际削弱筑城人数折扣

`0x489760`先取建筑基础费用B，统计参与者中满足筑城条件的人数K。原版费用为`floor(2B/(K+2))`；2026在`0x4897BD`接入位于`0x44F093`的助手，改为`floor(4B/(K+4))`。

K=0时两者均为B；K=1时由约66.7%B变为80%B，K=2时由50%B变为约66.7%B。它减少的是多人筑城带来的折扣，不能根据`codeLowerBuildExpense`这个名字宣称费用进一步降低。

<a id="companion-audit-33"></a>
### 计略、训练、修筑和施工的熟练度改动

若干恢复名中的“Experience”实际指兵法熟练度，写入的也不都是增量。2026的常驻写入结果如下：

| 行为 | 被改路径的原版收益 | 2026实际改动 |
| --- | --- | --- |
| 烧夷、夺取、救援计略 | 执行部队成员类别7、8各基础+2 | 跳过两次熟练度调用；这些路径不再给这两项收益 |
| 训练 | 各参与者类别0—4各基础+1 | 跳过五次调用 |
| 修筑 | 类别6、5各基础+1 | 跳过两次调用 |
| 设施施工未完成的每日进度 | 在队成员类别6基础+1 | 参数改为−1，被公共类别校验拒绝 |

这**不等于所有成长均取消**：烧夷/夺取/救援的其他能力成长和任务效果须沿各自路径判断。建设开工、完工的公共建筑结果奖励仍有类别6基础+3、人物统率成长尝试及筑城/造营学习路径；被取消的是未完工期间的那次日常+1。公共熟练度入口还会给类别精通者乘3，表中均为乘前基础值。

另有五个名带`Intelligence`的常量写入，实际修改的也是传给熟练度函数的类别号：离间/流言/激励把7改为6，伪报/扰乱把8改为6。它们不是智力属性成长概率；前置分支或其他助手可能跳过相应增长段，不能仅凭常量便宣称每次行动都获得完整奖励。

证据：`0x496A63`、`0x48DFF7`、`0x492E29`的短跳转；`0x48A2B8`与`0x4895C8`的跳过范围；`0x49C3F2`将`push 6`改为`push -1`；原版主库`0x460DC0`、`0x44DC80`、`0x44C920`、`0x49BFD0`和`0x49CB00`。参数写入集中在[安装末段](../src/runtime/RuntimeInjection2026.cpp:985)。旧帮助的成长描述不能直接替代这些现行字节。

<a id="companion-audit-36"></a>
### 象兵对步兵、骑兵兵法分别采用70%、60%效果

原版物理兵法效果函数`0x4FEB20`对步兵系攻击象兵直接返回15，即普通效果10的150%。伴侣同时修改类别门与返回值：类别0/1（步兵/骑兵）且目标有效阵型为象兵11时，返回`11-4-类别`，分别为7/6，即70%/60%。

因此它既取消步兵克象的150%分支，又加入对这两类兵法的不同抵挡效果；其他类别继续原有熟练度等判定。该返回值仍会进入完整伤害流程，不能理解成最终掉兵永远严格为某个未经取整结果的70%/60%。

证据：常驻字段`FootAntiElephant`在`0x4FEB30`把类别条件扩到0/1；描述符`0x424240`在`0x4FEB44`改返回值。两个改动须一起分析，单看其中一个会得出错误结论。

<a id="companion-audit-37"></a>
### 智力兵法“减损70%→50%”指抵挡后的效果值

原版共同效果函数在熟练度抵挡命中时返回3，未抵挡成功效果为10；伴侣把3改为5。因此效果保留比例由30%升为50%，也就是减损由70%降为50%，不是所有智力兵法最终伤害乘0.5。

主库交叉引用确认：辱骂、混乱、攻心、幻术、妖术调用共同函数`0x4FEBB0`；陷阱调用`0x4FED10`，两处都改返回常量。后续分别用于士气、混乱持续、兵损等各自效果，必须保留各兵法结算差异。独立的`0x504F8A`还将混乱持续计算中的熟练度分母250改为300；不要把两项混算成同一个倍率。

证据：[常量初始化](../src/generated/StateConstants.inc)、[安装写入](../src/runtime/RuntimeInjection2026.cpp:993)，原版主库的六个调用者及`resolve_confusion_tactic`。公共函数中的其他智力判定、兵法保护和阵型拒绝门仍需满足。

<a id="companion-audit-39"></a>
### 俘虏概率中的围攻数量改为分段增长

原版`0x44F3B0`中的数量项为`基础值B×N`。伴侣在`0x44F3F7`改为：取最小整数k使`k(k+1)/2 >= N`，再计算`floor(B×(N+k(k-1)/2)/k)`。N来自调用方交战数量输入，不是本旬计划出征队数。

例如N=1/2/3/6时，数量倍率分别为1/1.5/2/3（计算时整体整数截断），原版分别为1/2/3/6。归功方鹤翼加倍、人物前后排修正及宝物免疫等后续规则仍在。它减弱数量的线性放大，不等于取消围攻对俘虏的影响。

证据：[数量修正载荷](../recovery/evidence/payload_disassembly/00427DC8_000A3FE0_1F.asm)、描述符`0x427DF8`及原版主库`compute_capture_chance`。

<a id="companion-audit-41"></a>
### 普通出征及救援派兵的费用按兵数缩放

2026的两组常驻助手分别读取出征对话框的计划兵量与已构造单位的士兵数，将阵形基础费用C按`floor(C×兵量/16384)`缩放。两组描述符种子为`0x42F660`与`0x42F678`，调用方挂接分别在`0x4E9E25`、`0x460ABA`；两处不能只改一个而让界面与执行路径口径不同。

这是军队出发/派兵相关费用，不等同于单武将执行3000兵救援计略的成功率。新式会使少兵更便宜、多兵更贵；是否高于原固定费用取决于兵量和阵型基础数据，不能把“救援出征费增加”解释为所有情形都固定加收同一数额。

证据：`0x41FDE8`、`0x41FDF8`、`0x41FE40`、`0x41FE50`载荷与[种子初始化](../src/runtime/RuntimeVersion2026.cpp)。本项确认缩放算法，不把费用数据预设的变化混进算法数量。

<a id="companion-audit-24"></a>
### 玩家处斩普通俘虏时，按其最高能力扣减基础信望

旧版帮助原文：“处斩俘虏减少势力信望”。当前2026年实现只覆盖玩家势力执行普通俘虏处斩命令的路径，不能扩大为所有势力、所有处斩场景统一扣减。

扣减值为被处斩武将当前统率、武力、智力、政治四项中的最高值，除以12向下取整，再取至少2点；读取的是当前能力值，不是基础能力。例如最高能力35扣2点，80扣6点，100扣8点，120扣10点。扣除的是执行方基础信望，最低降到0，随后立即重算并写回势力总信望。总信望还有其他加成及1000上限，因此界面显示不一定恰好下降上述点数。

下达处斩命令时不扣，实际执行时才扣。补丁插在玩家势力专属的处斩对话生成前，扣减后继续原版对话及死亡处理。电脑执行同一命令会跳过该分支，即使被处斩者属于玩家，也不触发这项扣减；它不是死亡公共函数中的通用惩罚。

被俘君主的释放／处斩选择有独立处置流程，不经过该挂钩，不能据此认定处斩被俘君主也按同一公式扣信望。这项功能随基础补丁安装，没有独立开关，与“禁止电脑处斩俘虏”选项分开。2019年与2026年的扣减代码、公式和挂钩地址相同，未发现规则变化。

代码核对：伴侣`0x428E90`的46字节缓冲区由原版处斩命令`0x48B090`内的`0x48B0EB`调用；该位置位于执行势力玩家控制判定之后，传入人物为命令目标，执行势力保存在EBX。缓冲区调用`0x44D340`取当前四维最大值，除12并设最低2点，经`0x43DAD0`饱和扣减势力`+0x1C`基础信望，再以参数1调用`0x4432D0`重算写回总信望，最后转回`0x566ED0`生成原版对话。基础注入无条件安装`0x428ED0`描述符；被俘君主处置入口为`0x443FA0`。以上已与2019年源代码及san9-remake的`RE-SAN9PK-0132`核对，尚未实机验证显示变化。

<a id="diplomacy"></a>
## 外交与计略

<a id="companion-audit-6"></a>
### 离间玩家时，密商记录显示实际行动势力

旧版帮助描述：“电脑离间玩家势力时，进行记录中的密商势力名称显示错误”。

这属于伴侣作者对原版行为的判断。原版专门筛选第三方势力，并将其同时用于消息和关系变化，可能有意表达栽赃或挑拨，并不一定是程序错误；伴侣实际改变了这套规则。

原版离间会另选第三方势力，将其用于密商记录；离间成功后，还会降低目标势力与这个第三方的关系。没有合适第三方时，才使用实际行动势力。

优化伴侣跳过另选第三方的分支，始终使用实际行动势力。因此，这项改动不只是改名字：成功后的关系扣减对象也随之变为实际行动势力。离间本身降低目标武将忠诚度的效果仍保留。

代码核对：`0x4935EA`由条件跳转`74 51`改为无条件跳转`EB 51`，跳过第三方选择；保存的势力对象随后同时用于`0x493658`的密商文本和`0x4936E4`的关系变更。安装字段为`AlienateForceName`。

<a id="companion-audit-7"></a>
### 流言不再显示成密商，也不再额外降低武将忠诚度

旧版帮助描述：“电脑流言玩家势力时，进行记录中显示成密商，密商武将忠诚度下降”。这涉及消息显示与实际效果两部分。

原版有完整的武将筛选、智力判定和忠诚扣减逻辑，可能有意用“某武将与另一势力密商”的流言同时破坏外交关系和内部信任，并不一定是程序错误。“密商”措辞是否为文本误用仍无法确定，不能仅凭伴侣的说明认定原版实现有误。

原版在目标为玩家时，先用密商消息记录一名目标势力武将与另一势力的往来；该武将取自目标势力中当前忠诚最低的在职非君主武将。流言成功后，除了降低两目标势力关系，还可能按该武将智力判定，再扣其忠诚度3或4点。

优化伴侣分别跳过密商消息和额外扣忠诚的分支，保留流言的正常成败记录与势力关系变化。它没有把那条密商消息改写成流言，而是直接不生成该消息；取消扣忠诚也不限于电脑对玩家，玩家发动流言同样受影响。

代码核对：`0x493CED`由`74 21`改为`EB 21`，跳过密商消息9917；`0x493DBC`由`74 1A`改为`EB 1A`，跳过`0x493DD3`的扣忠诚调用。当前安装代码使用状态偏移6752和6740；应按实际地址辨别，两处历史字段名称容易混淆。

<a id="companion-audit-8"></a>
### 保留外交排名，避免电脑赠与、劝降的候选筛选失效

更新记录原文：“修复势力排行被错误清除，导致电脑后续无法尝试劝降/赠与的bug”。这里指AI使用的内部外交排名，不是界面的势力排行榜。

原版全局策略更新先给有效势力写入排名，随后在重建策略分组时又将同一批势力的排名清零。电脑赠与要求目标排名值大于己方，劝降要求小于己方；都为零时，两个严格比较都无法通过，导致候选筛选失败。排名值越大表示越靠前，通常表现为向排名更高者赠与、向排名更低者劝降；其他资格和概率条件仍需满足。

优化伴侣把`0x4BE3EC`改成`EB 08`，跳到`0x4BE3F6`，跳过清零参数及`0x4BE3F1`的排名写入调用，保留此前算出的排名。安装来自`0x42C134`数组的第5项。

san9-remake已经专门研究并处理此问题：外交排名快照与策略分组独立保存，首次使用前初始化，在规定更新时点重算，其他时段保留，并随存档恢复；保留赠与、劝降的严格排名方向。见san9-remake的`research/ai.md`“全局策略分组与外交排名”及`specs/original-ai/behavior.md`的B05。

原版已有正常存档中的非零排名也曾被实际消费，因此不能概括为“原版电脑始终不会赠与或劝降”；已确认的问题是上述更新路径会清除参与更新的有效势力排名。该条更新记录后半句关于君主相性影响成功率，是另一项改动，不包含在本节结论中。

<a id="companion-audit-9"></a>
### 外交难度与平衡性调整：劝降、赠与考虑君主相性差

更新记录原文：“计算劝降/赠与成功率时，考虑君主之间相性差的影响。”

本项属于优化伴侣对外交难度与平衡性的改进，调整了成功率和劝降条件。

伴侣读取行动方与目标方君主的相性，按150一圈取最短距离`d`（0～75），得到惩罚`p = floor(d / 5)`（0～15）。比较的是两位君主，不是使者与目标君主；相性越接近，惩罚越小。

赠与将原公式的关系加成`max(0, 关系值 - 60)`改为`max(-15, 关系值 - 60 - p)`，再加使者执行政治项和赠品项。因此不只是相性差会降低成功率：关系不足60时，即使相性相同，也可能出现原版没有的负修正。例如关系80、相性差50时，关系项由20降为10；关系50、相性差0时，关系项由0变为-10。

劝降在原公式的括号内减去`p`，之后仍乘使者执行政治值、再除60，所以并非统一扣除`p`个百分点。同一段修改还将最低整数兵力比从5倍降到3倍；不能只把它理解为增加相性惩罚。

代码核对：辅助代码`0x42C090`读取双方势力`+0xBC`的君主，再读君主`+0x6C`相性并计算惩罚；赠与通过`0x499076`调用注入辅助函数，并将`0x4990F1`的立即数改为`F1`，即`push -15`；劝降在`0x4913AD`开始的新代码中调用相性辅助函数，比较兵力比3，并扣除惩罚。安装来自`0x42C134`数组的第2～4项。

san9-remake目前保留原版成功率公式：赠与没有君主相性修正，关系项最低为0；劝降没有君主相性修正，最低兵力比仍为5。其“外交排名不被清除”的修复与本项规则调整相互独立。

<a id="companion-audit-38"></a>
### 电脑夺取资金：与目标现有资金相乘后除51200

原版夺取资金分支先算`B = floor((目标士兵+伤兵)/80) + rnd(50) + 10`，最后取`min(目标资金F, B)`。伴侣将这个最后的min调用接到控制权分流：执行部队的原虚槽`+0x3C`判断为玩家控制时保留原min；否则返回`floor(F×B/51200)`，正常数值范围内按原整数乘法执行。

因此电脑所得会随目标资金变化，F高于51200时可能高于B，较穷目标则更少；这不是统一加倍。原款项转移函数及成功概率仍另行处理。此处是执行部队控制权分支，不应不加核对地扩大成“所有玩家所属副军团都走玩家公式”。

证据：2026种子`0x42F618`四项载荷与`0x48E143`挂接；运行落点`0x461A24`、`0x461A42`、`0x494802`、`0x494485`；原版主库`execute_seize_command`。这解释了历史说明中玩家加强代码无效的边界：玩家没有使用这条乘资金的电脑分支。

<a id="companion-audit-40"></a>
### 离间的15日门与重复选择玩家目标

`0xA0A00`用人物所在单位/据点位置计算几何距离d，再取`floor((d+29)/30)`，超过15就从候选表删除。因此正常非负距离范围内相当于d≤450，是行程估算筛选，不是同一武将两次离间之间要等15日。它不使用完整寻路时间，不能当成“实际一定在15日内到达”的保证。

另一个助手在`0x4B12F2`截获候选消费：目标通过原玩家控制虚槽检查时保留候选，允许其他执行者继续选中；普通目标走原删除逻辑。它没有凭空生成额外行动次数，也不绕过人物可行动资格。

证据：[距离门](../recovery/evidence/payload_disassembly/004209C0_000A0A00_59.asm)、[重复候选](../recovery/evidence/payload_disassembly/004255E8_000A53B0_16.asm)。两者是独立条件，不应合并成一个冷却参数。

<a id="interface"></a>
## 编队操作与地图显示

<a id="companion-audit-4"></a>
### 运输队情报显示运输目的地，避免被交战对象替代

旧版帮助在“修正游戏bug”中列出：“运输部队的部队情报中，将交战都设显示为目标”。这里描述的是原版的错误现象。

例如，一支运输队原本要向A城运送物资，途中与B设施交战，原版情报里的“目标”可能显示成B设施，使人误以为运输目的地已改变。

优化伴侣改为读取运输命令保存的目的地，不再优先读取临时交战目标。上例中，情报仍显示A城。这是显示修正，不会把运输目的地改成交战对象，也不改变运输或交战命令本身。

<a id="companion-audit-14"></a>
### 选择计略、攻击目标时，用图标提示已有命令

更新记录原文：“调整大地图模式选择激励/救援/扰乱/伪报/攻击目标时的图标显示。”这是目标选择界面的显示调整。

伴侣绘制目标图标时，会扫描当前操作军团的有效部队，比较其命令目标是否为当前候选对象，再分别标记是否已有伪报／扰乱／激励／救援命令、是否已有攻击命令。没有查到相关命令时，保留原图标；查到时按计略、攻击或两者并存的状态换用相应图标，便于辨认已有安排。不会因此禁止继续选择该目标，也不改变命令及其效果。

代码核对：`0x42CFF0`辅助代码取得当前军团，按部队`+0x74`所属军团、`+0x50`命令目标与`+0x58`命令类型筛选；25～28归为四种计略，38归为攻击。计略标记选资源1252，攻击标记按入口选1238或1220，两类并存选1221；未命中保留原资源。三个调用点为`0x51FDDA`、`0x51FFEB`、`0x5201FC`，由`0x42D0C0`描述符数组安装。这里确认的是图标资源选择逻辑，尚未实机核对最终颜色与形状。

<a id="companion-audit-15"></a>
### 点击重叠对象时，默认直接打开完整列表

更新记录原文：“选择重叠设施/部队时，直接显示列表。”原版命中多个候选对象时先弹短菜单，对象较多时还需选择“更多”才能进入完整列表。伴侣默认跳过短菜单，直接调用完整对象列表选择界面；按住Alt时保留原菜单方式。只有一个候选对象时仍直接选择，不强制打开列表。

代码核对：在公共对象选择函数`0x418600`的多对象分支，`0x41868A`改调辅助代码`0x42C568`。辅助代码用`GetKeyState(VK_MENU)`检查Alt，未按住时调用完整列表入口`0x570440`，再返回原函数的选中对象处理路径。安装描述符为`0x42C5A8`。

<a id="companion-audit-16"></a>
### 坐标相同时，错开地图显示快照

更新记录原文：“部队坐标重叠时，避免部队信息条重叠。”伴侣生成地图标记快照时，扫描其他有效、非人员类部队的现有标记；若与当前快照坐标完全相同，就将当前快照两轴坐标各加5后返回，不写回部队实际行军坐标。

这是一次性的坐标错位，不是按信息条矩形做完整避让，也不会偏移后重新检查。因此不能保证多支部队密集重叠时，所有信息条都能完全错开。

代码核对：`0x5300E1`接入辅助代码`0x42C4F0`，修改当前显示快照`+4/+8`坐标；扫描其他部队对应的地图标记坐标，首次命中后各加5并返回。安装描述符为`0x42C550`。此轮确认了数据路径，尚未实机核对视觉偏移量。

<a id="companion-audit-17"></a>

### 记住出征搭配，并用快捷键恢复成员和配置

2019年7月新增组队记忆；2022年1月增加循环选组快捷键，7月增加阵型、船只、兵数及阵位顺位的记录与恢复；2025年12月又写有“优化自动组队代码对阵型位置的记录”。以下按当前2026年样本说明，不把各版行为混在一起。

2019年代码在攻击出征且人数大于3时，按大将编号和队内统率顺序给人物写入组队序列。当前记录器改挂在公共出征执行链，只在人数为4或5时记录，内部没有另行检查玩家身份或攻击命令。记录随人物保存，不是独立的固定编队名单；同一主将先后带过不同副将，仍保留其标记的人可能混在同一组，最多只选5人。它不按相性、亲密度或兵法连锁重新搜索最佳搭档。

出征配置界面按反引号键（Esc下方、数字1左侧的按键），按组队顺序选择当前可用的已记录主将及其成员，并恢复配置；继续按选择下一组，末组之后回首组；按住空格再按则倒序选择，首组之前回末组。没有可用的已记录主将时退出。旧的“清空选择后点击执行武将”入口仍只负责自动选人，要求找到至少3名同组成员，不执行整套配置恢复。

恢复时先收集同组成员，按保存的阵位顺位排列，最多保留5人，再根据实际成员重建可用陆阵和船只列表。记录的陆阵、船只仍可用时恢复它们，否则分别退回长蛇、走舸。更换据点、成员或兵法来源后，原配置不一定仍然可用。

兵数保存的是档位。10000～44999人按5000向下取整，分别恢复10000、15000、20000、25000、30000、35000、40000人；不足10000或达到45000以上时，不应用记录档位。恢复先按当前主将带兵上限和据点现兵数取较小值，再在记录档位低于该值时降到档位。例如上次28000人记为25000，这次最多只能出18000人，最终仍为18000人；超出记录范围时保留本次最大可出兵数。

阵位记录保存人员顺位，并记下是否空出阵型第一个默认位置。恢复时按顺位依次填入该阵型五个默认位置；人数不超过4且带空首位标记时，从第二个位置开始放人。它不能逐格恢复任意空洞，也没有独立保存一套历史兵法清单。不同组按主将统率组织，组内改按阵位顺位排列；武将一览的组队排序入口从2019年的“武将”↓改为“武将”↑。

无效组队记录的清理由2019年的读档时移到存档时，包括自动存档。当前会清除非玩家、身份不合格人物的记录；未出征人物还要求所属据点内至少有3名同组未出征人物，否则清除。旧说明写“小于2人”，但旧代码及当前样本均以至少3人为保留门槛；已出征人物跳过据点人数检查。

代码核对：游戏`0x48C030`接入记录器，伴侣缓冲区`0x4294F0`写人物`+0x104`的成员／配置记录及`+0xA0`排序值；`0x42A798`中的反引号处理分支恢复选组、阵型、船只、兵数和阵位。`0x429690`保留点击执行武将的选人流程；`0x429798`的清理入口接在`0x45B2E7`存档人物序列化调用处。以上缓冲区内引用的`0xAxxxx`为基准注入地址，实际运行会重定位。

<a id="companion-audit-19"></a>
### 按阵型自动配兵法，并支持单将切换和全队配置

2019年4月增加自动配置兵法，7月移除独立选项并默认加入；后续增加出征配置界面的Q/W/E/R/T快捷键。鼠标指向单将与移开后的全队配置走不同规则，不能把两者都理解为循环切换。

鼠标选择阵型并确认时，鱼鳞／鹤翼对应步兵，锋矢对应骑兵，长蛇对应弓骑，雁行／井阑对应弩兵，方圆对应智力兵法；其他阵型不执行这段重配。对上述阵型，若人物基础智力减基础武力严格大于15，改选智力类，恰好相差15不触发。

物理类分别按奋迅→奋斗→奋战、突击→突进→突破、飞射→奔射→骑射、连弩→连射→齐射选择。智力类优先级为幻术→妖术→治疗→攻心→教谕→陷阱→混乱→破陷→鼓舞→辱骂。逐项检查本人已习得、宝物附加及势力提供的兵法，找到第一个可用项就装备；全部不可用时保留原兵法，不再跨类兜底，也不比较熟练度、实际伤害或队友联动收益。

Q/W/E/R/T分别指定步兵／骑兵／弓骑／弩兵／智力类。鼠标没有指向人物面板时，对本次已选出征人物逐个执行上述优先级配置，仍保留智武差大于15时转智力类的规则，只是类别来自按键而非阵型。因此批量按Q不保证人人装备步兵兵法；转智力类后无可用项也不会回查步兵类。连续按同键通常结果不变，空格不改变批量配置方向。

鼠标指向有人物的面板时，只处理该人，按指定类别建立可用兵法列表，再以当前装备为起点选下一项，末项之后回首项；按住空格再按则选上一项，首项之前回末项。当前兵法不在候选列表中时选首项，即使按住空格也如此；没有候选则保持原样。该模式不检查智武差，高智低武人物也可明确切到物理兵法。

单将物理类按高级到低级循环，跳过不可用项；单将T按兵法编号倒序，实际为妖术→治疗→鼓舞→辱骂→幻术→攻心→陷阱→混乱→教谕→破陷。它与批量T优先幻术的顺序不同。例如某将只会奋迅、奋战，指向他连续按Q会在两者间循环；移开鼠标批量按Q则每次优先选择奋迅。

代码核对：`0x4E9207`接入伴侣`0x429220`自动配置缓冲区；基准入口`0xA7C4D`执行智武差与优先级选择。`0x42A798`中的Q/W/E/R/T分支扫描五个人物面板，未命中单将时逐人调用该公共入口；单将分支通过`0xA8CA0`建立候选，再调用`0xA8BF0`循环选择。原版`0x44F770`／`0x44E170`确认本人、宝物及势力的兵法来源。

### 用1～6/Y切换阵型和船只，保留兵法配置

更新说明将出征配置快捷键1～6/Y概括为步兵、骑兵、弓骑、弩兵、长蛇／方圆、攻城和船只。当前实现按固定分组筛选已有可用列表，不会解锁不可用阵型，简称也不等于组内只有一种兵种。

| 按键 | 分组接受的普通陆阵 | 另接受的异民族陆阵 |
| --- | --- | --- |
| 1 | 鱼鳞、鹤翼 | 倭、山越、南蛮专用陆阵 |
| 2 | 锥形、锋矢 | 乌丸、羌专用陆阵 |
| 3 | 锥形、箕形、长蛇 | 乌丸专用陆阵 |

<a id="companion-audit-21"></a>
### 用Z/X/C/V重排人物，按前排位置判定先锋

更新说明将Z/X定义为按武力／智力排列，C为把最高智力人物放到第一个非先锋位，V为人数不超过非先锋位数目时从第一个非先锋位开始配置。当前实现还有非先锋位不够用时的后备安排。

先锋按九宫格阵位编号判定：0、1、2为前左、前中、前右，属于先锋；3～5为中排、6～8为后排，属于非先锋。“第一个非先锋位”是按当前五个配置栏顺序找到的第一个编号大于2的位置，不是固定的第四栏，也不一定是中央位置。这些按键保留每栏的阵位编号，只重新安排人物。

Z按人物武力属性、X按智力属性降序排列，再从第一栏依次填入，人数不足时末尾留空；同值保留原配置栏的相对顺序，不追加统率或人物编号比较。它们不避开先锋位，X可能把最高智力者放到先锋。连续按键不切换升降序，空格也不反转排序。

C先按当前栏序找到智力最高的一人，放到第一个非先锋位，再把其余人物按原相对顺序从第一栏填入，遇到预留位置就跳过，未填位置留空。它不检查正式军师身份或智武差；智力相同时取先遇到的人。例如锋矢五栏对应前左、前中、前右、中中、后中，原人物为甲、乙、丙、空、空，乙智力最高时，按C后为甲、丙、空、乙、空。它只把最高智力者后置，其他人物仍优先从前面填。

V保留人物原相对顺序。人数不超过非先锋位数量时，从第一个非先锋位依次放人，先锋全部留空；人数更多时，改用五栏中的最后N栏，前面5−N栏留空，仍可能占用先锋。例如鱼鳞三人排为空、甲、乙、丙、空；锋矢两人排为空、空、空、甲、乙，三人则为空、空、甲、乙、丙，其中甲仍在前右先锋位。V不能保证任意人数下都清空前排。

四个键均不换阵型、船只或兵法。需要高武人物靠前并将最高智力者后置时，可先Z后C；少人数尽量避开先锋时用V。之后再按1～6换阵，会重置各栏阵位，可能改变刚才的后置效果，应重新检查或安排。

代码核对：Z/X/C/V分别以模式0～3进入`0x42A798`中的共享入口`0xA8EA0`。该入口扫描五栏，按阵位`>2`收集非先锋位置；Z/X经原版`0x46F640`按属性28／29稳定降序排序；C经`0x473130`取智力最大者，同值不替换先取人物；V按非先锋位数和人物数选择目标栏。最终清空并写回人物指针，再调用`0x4E8400`刷新。默认阵位例子与san9-remake的`RE-SAN9PK-0017`及原版剧本阵型记录核对，尚未实机验收。

## 存读档、对象状态与证据边界

<a id="companion-audit-2"></a>
### 港口换成其他建筑后，近战船仍能交战

更新记录原文：“修复替换港口位置建筑后，走舸/异船无法与之交战的bug。”（2025年12月）

原版对部分近战船额外检查目标是否为港口。把港口换成其他类别的建筑后，即使船能够靠近，相关判定也会返回零射程，使攻击失败。

优化伴侣把这个失败出口改为返回船只的基础射程。因此，它实际取消了这一层目标类型限制，范围比“只允许攻击原港口位置上的替换建筑”更宽；距离及其他交战条件仍需满足。

船名沿用更新说明；现有名称映射与该分支的编号对应存在差异，具体船名仍需实机核对。

<a id="companion-audit-5"></a>
### 倭未出现时，在相关区域使用中继点不再退出

更新记录在2022年1月写有：“修复45号城市倭未出现时，在倭/末芦下属区域使用中继点导致游戏退出的bug。”2025年12月又写有“重新修复”。以下核对的是当前2026年样本的实际实现，尚不能单凭现有样本区分两次修复各自改了什么。

倭未出现时，倭城及末芦港尚未启用，但相应地图区域仍然存在。原版设置中继点时，先查询地图块所属的有效城港，再立即读取城港编号，用于倭、末芦的特殊路线限制。前一步可能返回空指针，后一步没有检查，因而导致退出。

优化伴侣直接跳过整段特殊限制，进入正常的中继点路线计算。它既避开了空指针访问，也取消了这段倭、末芦专用限制；并非仅补一个空指针检查，也不会提前启用倭城。前面的地形障碍等检查仍保留。

代码核对：原版入口`0x4F5640`中，`0x4F573D`调用`0x45C8A0`查询所属城港，其下层`0x454DF0`会将未启用对象判为无效并返回空指针；`0x4F5742`随即执行`mov edx,[eax]`，没有判空。伴侣描述符`0x42B568`将`0x4F573B`处5字节改为`E9 88 00 00 00`，跳到`0x4F57C8`，继续调用`0x4F6640`计算并显示中继路线。安装位置见`RuntimeInjection2026.cpp`的`writeDescriptor(0x42B568u, ...)`。

<a id="companion-audit-10"></a>
### 读档先恢复建筑类型，避免按旧类型截断兵力

更新记录指出：读档先设置兵力、后设置建筑类型，兵力上限可能误用对应剧本的原建筑类型；原位置若为障碍物，就会清除存档兵力。

例如，剧本某位置原本是障碍物，游戏中已换成可以驻军的建筑并保存。读档时若先写兵力，当前对象仍是旧类型，就会按错误上限截断；之后即使恢复了正确建筑类型，也无法找回已丢失的兵力。原版存在这个设置顺序问题；原版普通非城市上限统一为25万，并非障碍物上限为零。伴侣细分建筑上限、将障碍物上限设为零后，这个问题表现为清兵。

伴侣在恢复兵力前，先从存档游标后方预读建筑类型，写入当前对象，再调用正常的兵力设置函数。它保留容量检查，让检查使用存档实际类型，而非绕过上限；后续仍按原格式正常读取字段。

代码核对：原版设施读档函数`0x4377E0`在`0x437834`调用兵力setter`0x4373A0`，建筑类型在后面才恢复；setter会调用`0x4361C0`取当前类型的容量。伴侣将该调用改为进入`0x437398`：从`[edi] + 0x17`预读类型，再经`0x4373C2`调用类型查询`0x453760`，写入建筑`+0x48`，最后回到`0x4373A0`设置兵力。安装来自`0x425840`数组的第5、6项，以及`0x4258D0`数组的第2项。

san9-remake从完整存档快照恢复建筑状态，不通过“先加载剧本旧类型、再逐字段调用兵力setter”的流程，因此没有这条按旧建筑类型截断兵力的路径。

<a id="companion-audit-11"></a>
### 在建设施的输送资格

更新记录原文：“修复优化下电脑向周围有敌部队的在建设施输送兵力的问题。”措辞明确针对优化环境下的运输决策，不能直接归为原版运输错误。

已核对的原版运输账本函数`0x4BBF50`通过`0x4AF210`排除在建设施，并将其账本值清零。伴侣保留这道资格检查，另在`0x4BC0CE`接入重写的余缺兵力计算，并用`0x4251F4`的辅助代码建立运输来源、目标列表；账本为零时不会加入列表。因此当前核到的这条路径会排除在建设施，并非只在周围有敌军时才排除。尚未定位更新记录中那一次修复的独立改动，不能将这道原版已有检查直接当作新增修复。

san9-remake的AI运输来源与目标共用`OriginalAiMilitary.Places`，要求建筑未停用、未摧毁、能容纳人员且没有建设部队（`BuilderUnitId`为空）。因此在建设施不会进入AI运输候选，无须先判断附近有无敌军。这不代表AI完全禁止向受威胁的已完工据点输送兵力。

<a id="companion-audit-12"></a>
### 仲裁失败不再误用未初始化的增兵奖励

更新记录原文：“修复特定势力武将探索特定地域触发仲裁事件时，仲裁失败导致武将所属都设兵力溢出（可能为负值）的bug。”对应探索事件53“贼归顺”。

原版分别保存特殊君主／地点匹配标志、仲裁成败和增兵奖励，但奖励数只在仲裁成功时赋值，构造时未初始化。提交阶段却先判断特殊匹配，再判断成功：匹配特殊条件时，仲裁失败也会进入奖励分支，把未初始化的数当增兵量写入探索武将所属都设，可能造成异常兵力。不是正常扣兵公式减成负数。

伴侣改为先检查仲裁成功，失败统一减信望并受伤；只有成功后才区分普通奖励和特殊君主奖励。同时将成功增兵量限制为当前建筑剩余容量，容量不足时最低为零，再保存实际奖励数。

代码核对：原版演出`0x581960`仅在成功分支写奖励字段`+0x4C`；提交`0x581CD0`原先优先检查特殊标志`+0x44`。伴侣在`0x581D03`先比较成功字段`+0x48`，失败跳到`0x581D84`，再检查特殊标志；`0x581BF5`起的新代码计算并保存受剩余容量限制的奖励。安装来自`0x42CADC`四项数组。

san9-remake已专门研究并采用正确的成功／失败顺序：失败没有增兵及特殊金钱奖励，按普通失败结算；成功才按容量增加兵力。`SearchConflictTests.FavoredLeaderRewardsOnlySuccessfulMediation`覆盖特殊君主在武力、和平两种仲裁中的成功和失败。

<a id="companion-audit-13"></a>
### 新局部队初始化

旧版帮助在修正游戏bug中列出：“开始新游戏时，未完全初始化全部队”。该说明没有列出具体遗漏字段或触发现象。

已沿上下游核对普通新局加载链：`0x45C1A0`先调用`0x453DA0`重置场景，加载剧本及人物／宝物覆盖数据，再以参数1进入`0x45AE90`完成关联与新局派生状态。重置阶段，部队池循环处理850个槽，通过虚表`+0x14`调用`0x4615E0`；城市、设施的重置也会重置其内嵌驻军。后续新局分支调用`0x459880`设置有效部队的人物排列、标志及默认船只，最后重建地图占位；配置确认还另经`0x45C120`处理玩家选择及新局选项。不能只凭850次循环就认定整个初始化正确，也不能将此说明解释为漏掉最后一个槽；在当前核到的普通新局路径上，尚未发现跳过完整重置的调用。伴侣对应的独立修改及具体遗漏字段仍未定位。

san9-remake的新局创建使用新的`WorldState`，从剧本初始数据建立独立部队集合，不沿用上一局的全局固定部队池。这避免了复用旧部队槽但未清干净的状态残留路径；不等于已经复现并定位原版此项错误。

<a id="companion-audit-22"></a>
### 将五份循环自动存档写入最后五个用户存档位置

旧版帮助原文：“用户存档的最后5个存档保留作为游戏的自动存档”。原版已有五份循环自动存档，伴侣没有另加定时保存器，而是保留原版触发流程，把文件名从`D_Auto00.S9`～`D_Auto04.S9`改为`D_Sav035.S9`～`D_Sav039.S9`，对应界面第36～40个用户存档位置。这些位置会被自动保存覆盖，不是额外增加五个槽。

轮换序号为`floor(距剧本开始经过的游戏天数 / 10) % 5`。正常每旬换到下一份，五旬后覆盖同一位置；不是按现实时间间隔保存，也不是每次启动程序递增一个槽。回到旧日期重新推进，仍按该日期选择保存位置。

自动存档发生在旬行动入口需要重新建立势力行动列表时：没有有效当前势力游标，程序便建立并排序本旬列表，写回世界状态，然后保存，再安排全局策略准备及本旬行动。因此保存的是本旬行动入口状态，不是玩家安排完命令后的状态；已有有效游标时只恢复当前势力操作，不执行这次保存。

正常新开局会在完成设置、进入首旬流程时立即自动保存，不必先点击“进行”。原因是新局重置清空了行动列表，首旬必须重建；正常首日经过天数为0，首先写入`D_Sav035.S9`，即第36个用户存档位置。这里的“立即”指进入首旬流程时，不是仍在剧本选择或开局设置界面时。

正常读入手动或自动存档，不会因读档本身立即再保存一次。存档包含尚未完成的势力行动列表，读入后重建该列表，旬入口已有有效当前势力，因而走恢复分支。自动存档本身也在新列表写回后才生成，所以重新读入它不会再次作为空列表的新旬入口保存；之后正常推进到下一旬仍会保存。若特殊存档恢复后没有有效游标，则可能进入重建与保存分支，不能把“不立即保存”扩大为所有存档状态的保证。

代码核对：原版`0x45B4D0`按`0x454B10`取得的经过天数计算五槽序号；伴侣在`0x45B50E`接入`0x4255A8`，原地改写文件名后继续正常路径处理和`0x45B3C0`写档。旬入口`0x50EC90`仅在无有效当前游标的分支，经`0x50F041`写回行动列表，再由`0x50F046`调用自动保存。新局重置`0x453DA0 → 0x46AB30`清空列表；存档读入分发函数在`0x457BE8`恢复列表，随后沿既有游标继续。以上为当前样本静态调用链结论，尚未实机观察文件写入。
